# 性能

Apple M4（10 コア、メモリ 16 GB）での、Rust エンジンの測定値である（5 回の中央値）。
データは乱数で作ったもので、実行ごとに 2 割程度ばらつく。

損益計画と人員計画（`examples/fpa.py`、計算 Metric 18 個）：

| 規模 | 全セル数 | 全体の再計算 | 給与を 1 人変更 | 1 人を異動 | 社員を 1 人追加 | 締め月を 1 か月進める |
|---|---|---|---|---|---|---|
| 社員 2 千、商品 500 | 49 万 | 13 ms | 0.3 ms | 0.1 ms 未満 | 0.3 ms | 5.1 ms |
| 社員 2 万、商品 5 千 | 490 万 | 87 ms | 0.4 ms | 0.1 ms | 0.3 ms | 50 ms |

締め月を進めると、その月の全社員と全商品の見込みが実績に置き換わる。
計算し直す量が変わる値の量（約 6 万セル）に比例するので、他の変更より時間がかかる。

同じモデルで、メンバーの名前を変えたり消したりした場合：

| 規模 | 社員の名前を変更 | 社員を 1 人削除 | 商品を 1 つ削除 | 部署を 1 つ削除 | 途中の月を 1 つ削除 |
|---|---|---|---|---|---|
| 社員 2 千、商品 500 | 0.1 ms | 2.1 ms | 1.6 ms | 11 ms | 16 ms |
| 社員 2 万、商品 5 千 | 0.2 ms | 10 ms | 4.3 ms | 56 ms | 230 ms |

部署を消すと、その部署に所属していた社員（全体の約 3 分の 1）の所属が空になり、人件費と人数の集計を計算し直す。
途中の月を消すと、その月以降の累計と資金、通年の集計がすべて変わるので、全体の再計算と同じくらいかかる。

計算 Metric の数を増やしたモデル（`bench_metrics.py`）：

| 計算 Metric 数 | 全セル数 | 全体の再計算 | 1 セルの変更（計算し直した Metric 数） |
|---|---|---|---|
| 300 | 2522 万 | 516 ms | 1.4 ms（95 個） |
| 1000 | 7699 万 | 1,150 ms | 4.6 ms（394 個） |

同じモデル（1000 Metric）で定義を変えた場合（変える前は、どれも全体の再計算の約 1,350 ms かかっていた）：

| 定義の変更 | 時間 |
|---|---|
| 式を 1 つ足す | 7.2 ms |
| 下流 64 個の式を置き換え、全セルの値が変わる | 157 ms |
| 下流 64 個の式を置き換え、1 商品だけ値が変わる | 7.8 ms |
| 下流 529 個の式を置き換え、全セルの値が変わる | 365 ms |
| 下流 529 個の式を置き換え、1 商品だけ値が変わる | 25 ms |

損益計画（490 万セル）では、式を 1 つ足すのに 6.0 ms、売上原価の式を 1 商品だけ変えるのに 7.3 ms、全商品で変えるのに 15 ms かかる。

Metric の数そのものを増やした場合（`bench_layout.py`、1 回の測定）。
鎖は `x{i} = x{i-1} + 1` を 1 つのトランザクションでまとめて足すモデル、もう 1 つは入力 `x{i}` と式 `y{i} = x{i} + 1` を 2,500 組持つモデルである。
「作り直し」は、計画を捨てて全体をコンパイルし、全 Metric を計算し直す時間で、記録先から開くときや、軸や種類を変えたときと同じ流れである。

| モデル | Metric を足す | 作り直し（コンパイルと全体の再計算） |
|---|---|---|
| 鎖 2,000 本 | 0.07 s | 0.03 s |
| 鎖 5,000 本 | 0.19 s | 0.09 s |
| 鎖 20,000 本 | 0.83 s | 0.48 s |
| 入力 2,500 + 式 2,500 | 0.26 s | 0.57 s |

以前は、分割軸を選ぶたびに全 Metric の状態を 1 周していたので、Metric の数の 2 乗で遅くなった（鎖 20,000 本で、足すのに 60 秒、作り直しに 32 秒）。
いまは、各入力の 1 セルを変えたときの影響範囲（[分割軸の選び方](engine.md)）を、Metric ごとの一覧に 1 回だけ組み替えて使う。
入力の多いモデルの作り直しで残る時間の大半は、入力ごとにその影響範囲を伝える費用である。
1 回の伝搬は計画の全段階を回るので、この費用は入力の数と Metric の数の積に比例する。
入力と式の組を倍にすると約 4 倍になり、入力の多いモデルでは 2 乗が残る。

セル数を増やした小売モデル（`bench.py`、1756 万セル）では、全体の再計算が約 1.7 秒、1 セルの変更が 1 ms 未満、1 商品の価格の変更が約 12 ms（カテゴリの集計が全店舗と全月で変わる）である。

版を公開しながら書き込む場合（`bench_versions.py`）も測る。
トランザクションごとに公開済みの版を複製し、複製に書き込んで再計算し、次の版として公開する流れである（複数の利用者が同時に書き込むときの単一ライターを想定している）。

| 変更 | その場で書き込む | 版を公開しながら書き込む |
|---|---|---|
| 1000 Metric、1 セル | 6.2 ms | 7.5 ms（うち複製 1.0 ms） |
| 損益計画（490 万セル）、給与を 1 人変更 | 0.4 ms | 0.6 ms（うち複製 0.2 ms） |

格納データの本体を共有する前は、複製した後の最初の書き込みで、再計算した Metric の格納データを丸ごと写していた。
そのため、1000 Metric の 1 セルの変更は 342 ms かかっていた。
複製の残りは Python 側で Metric の定義を写す時間で、Metric の数に比例する（1000 Metric で約 1 ms）。
トランザクション（`transaction`）の費用も、この複製と前後の差を求める時間で、1000 Metric のモデルの 1 セルの変更は 6.2 ms から 7.7 ms、損益計画の給与の変更は 0.4 ms から 0.7 ms になる。
記録をディスクまで確実に書き出す（macOS では `F_FULLFSYNC`、ほかでは fsync）と、この手元の環境（macOS の SSD）では 1 件の確定あたり約 3 ms かかる。
損益計画の給与の変更なら、記録つきで 4.0 ms になる。
多数の利用者の書き込みを受けるときは、複数のトランザクションをまとめて書き出す仕組み（グループコミット）が要る。
（入力する値が上の表と違うので、その場で書き込む場合の時間も上の表と少し違う。）

読み出し（`bench_reads.py`、損益計画（大）、PayrollByEmployee は 137 万セル）：

| 読み出し | 時間 |
|---|---|
| `value` で PayrollByEmployee を丸ごと Cube に | 483 ms |
| `get` で PayrollByEmployee の 1 セル | 0.01 ms 未満 |
| `slice` で 1 商品の全版・全月（Revenue） | 0.02 ms |
| `rows` で 1 部署の先頭 50 行（Payroll） | 0.02 ms |
| `summarize` で売上の月別合計（全商品） | 2.2 ms |
| `save`（スナップショット、入力 102 万セル） | 33 ms |

`get` が読み出し API になる前は、1 セル読むのにも `value` と同じ約 500 ms かかり、その間 GIL を握っていた。
`save` も Python で全セルを走査していて約 500 ms かかった。
`save` は Parquet にしてから 11 ms から 33 ms に増えたが、大きさは 17.9 MB から 1.4 MB になった（[保存と記録の形式](#保存と記録の形式)）。

8 人の読み手が休みなく読み続ける中での書き込み（給与を 1 人変更、単独なら 0.6 ms）は、通常の Python では読み手が `get` でも中央値 84 ms かかる。
読みの費用ではなく、ライターが GIL を取り直すたびに Python のスレッド切り替えの間隔（既定 5 ms）を待つためで、`sys.setswitchinterval(0.0005)` にすると 8 ms になる。
free-threaded の Python（3.14t）では GIL がないので、同じ状況で 2.9 ms になり、切り替えの間隔をいじる必要もない。

| 計測（損益計画 大） | 通常の Python 3.14 | free-threaded 3.14t |
|---|---|---|
| 8 人が休みなく `get` する中での書き込み | 84 ms | 2.9 ms |
| HTTP で 8 人が休みなく読む中での書き込み | 2.0 ms | 2.3 ms |
| その間の HTTP の読み出し | 毎秒 2,200 件 | 毎秒 9,700 件 |
| スナップショットの保存 | 33 ms | 39 ms |
| 全体の再計算 | 133 ms | 128 ms |
| 給与を 1 人変更 | 0.4 ms | 0.4 ms |
| HTTP の書き込み（単独） | 0.8 ms | 1.8 ms |

1 本のスレッドの処理は同じ速さで、HTTP の書き込みの単独の時間だけ free-threaded の Python の固定費で 1 ms ほど増える。
読み手が多い状況では、読み出しの件数が 4 倍を超え、書き込みは待たされない。

メモリの内訳（`bench_memory.py`、損益計画（大）を 4 倍にした 1,965 万セルを、スナップショットから開いて全体を計算し直す）：

| 計測 | 1 セルあたり |
|---|---|
| 格納データ（本体 16.0 B、分割軸以外の索引 1.6 B） | 17.6 B |
| Rust のヒープ（計算し直した後） | 17.6 B |
| Rust のヒープの最大（計算し直す間） | 28.6 B |
| 同上、1 スレッドで計算したとき | 25.2 B |
| RSS（計算し直した後） | 58 B |

格納データはキーと値の 16 B にほぼ等しく、計算し直した後に Rust が持ち続けるのは格納データだけである。
計算し直す間の途中結果を含めても、ヒープの最大は格納データの約 1.6 倍で済む。
集計を読みながら行う前は、最大が 1 セル 98.6 B（格納データの約 5.6 倍）あった。
社員 × 月の人件費（551 万セル）を部署へ集計する式 1 つが、読み出し、対応表、結合の結果、集計前の並べ替えの各段で全件を写し、531 MB を使っていたためである（今は対応表の配列の 12 MB）。
同じ変更で、全体の再計算は 577〜615 ms から 393〜419 ms になった。
小売モデル（1,756 万セル）では、再計算中のヒープの最大の増え幅は 6.6〜7.1 GB から 5.2〜6.6 GB になったが、格納データ（879 MB）の 6 倍を超える。
こちらは集計ではなく、1,756 万セルの途中結果を演算ごとに作ることが大半を占める。

RSS が Rust のヒープより大きいのは、macOS の標準のアロケータが、解放した大きなブロックを使い回し用に抱えるためである（`vmmap` の MALLOC_LARGE (empty)）。
集計を読みながら行う前の版では、計算し直すたびに増え（1 回目 1,919 MB、4 回目 2,559 MB）、環境変数 `MallocLargeCache=0` を付けて起動すると 791〜812 MB で止まった（再計算の時間は変わらない）。
RSS は実行ごとに大きくばらつくので、使っているメモリを比べるときは Rust のヒープで比べる。
Rust のヒープは `nanashi_core.track_heap(True)` の後の分を `nanashi_core.heap()` で、Metric ごとの格納データは `m.memory()` で読める。
数えている間は確保のたびに原子的な加減算をするので、既定では数えない（数えると並列の再計算が数 % 遅くなった）。

記録先を比べると次のとおり（`bench_journal.py`、損益計画、PostgreSQL は手元の Docker）。

| 計測 | ファイル | PostgreSQL |
|---|---|---|
| 1 件ずつトランザクションで確定 | 中央値 5.9 ms | 中央値 1.6 ms |
| `Workspace` に 8 人が同時に書き込む | 毎秒 517 件、中央値 15 ms | 毎秒 681 件、中央値 11 ms |
| 10 万セルの変更を確定 | 43 ms | 27〜44 ms（履歴の表への反映は確定の後に 0.4〜0.5 秒） |
| 100 万セルの変更を確定 | 375 ms | 152〜167 ms（同 4.2〜6.4 秒） |
| スナップショットと 1000 件の記録から開く | 0.14〜0.19 秒 | 0.18 秒 |
| 1 つのセルの履歴を引く（履歴 300 万行） | 記録を先頭から読む | 0.2 ms |

小さな確定で PostgreSQL が速く見えるのは、書き出しの確かさが違うためである。
ファイルは macOS の `F_FULLFSYNC` で装置のキャッシュまで書き出す（1 回約 3 ms）。
Docker Desktop の PostgreSQL は仮想マシンの中で書き出していて、1 回 52 マイクロ秒で終わる（`pg_test_fsync`）。
これは物理的な装置まで届いていない速さで、この環境の PostgreSQL の確定は電源断に対して確実とは言えない。
本番の環境（ディスクへの書き出しとネットワークの往復がある）では、確定の時間は数 ms 増えると見込むので、測り直す必要がある。

## 保存と記録の形式

スナップショットと大量の変更のファイルを npz から Parquet にし、大量の変更を変更の塊のまま運ぶようにした前後の比較（損益計画（大）、PostgreSQL は手元の Docker、Python 3.14）。
「社員 × 月の賞与を登録」は 72 万セルの入力 Metric を足す書き込み、「販売数量を按分」は 22.5 万セルを書き換える書き込みで、どちらも `Workspace` を通した時間である。

| 計測 | 変更前 | 変更後 |
|---|---:|---:|
| スナップショットの保存 | 11 ms | 33 ms |
| スナップショットの大きさ | 17.9 MB | 1.4 MB |
| スナップショットの読み込み | 14 ms | 15 ms |
| 社員 × 月の賞与を登録（PostgreSQL） | 2,023 ms | 485 ms |
| 社員 × 月の賞与を登録（ファイル） | 1,976 ms | 762 ms |
| 販売数量を按分（PostgreSQL） | 4,152 ms | 88 ms |
| 1 セルの書き込み（PostgreSQL、中央値） | 3.3 ms | 3.1 ms |
| 大量の変更のファイルの大きさ（PostgreSQL） | 33.9 MB | 0.8 MB |
| 確定の後の履歴の表への反映（PostgreSQL） | 4,027 ms | 2,925 ms |
| 上の書き込みの後で、スナップショットと記録から開く（PostgreSQL） | 1,943 ms | 115 ms |
| 同上（ファイル） | 1,873 ms | 1,793 ms |
| 賞与の 1 セルの履歴を引く（PostgreSQL） | 22.5 ms | 8.1 ms |

PostgreSQL の記録先から開く時間が 1/17 になったのは、大量の変更を Parquet から変更の塊として読み、Rust でまとめて書き込むからである（変更前は npz を Python のリストに直し、1 セルずつ書き込んでいた）。
ファイルの記録先は、このときはまだ変更を JSON の行で持っていたので、開く時間はほとんど変わらなかった（次の表で直した）。
按分の変更後の値は、`spread` をまとめて書き込むようにしたあとのものである。
Parquet にした時点では 3,814 ms かかっていて、ほぼすべてが 22.5 万回の `set_cell` だった（記録の費用は 1 割に満たない）。
今の `spread` は、範囲のセルを軸ごとのメンバー番号の列のまま読んで配り、エンジンの `write_many` で 1 回で書き込み、変更範囲も 1 回で広げる。
`spread` 単独では 3.6 秒から 22 ms になった（Python 3.14t でも 3.7 秒から 25 ms）。
スナップショットの保存が遅くなったのは Parquet の符号化と圧縮のためで、保存は既定で 1000 件の記録ごとに別のスレッドで行うので、書き込みは待たされない。

ファイルの記録先も、大量の変更を JSON の行にせず、`PgJournal` と同じ Parquet のファイルに書くようにした前後の比較（同じ損益計画（大）、`Workspace` を通した時間）。
変更前は、按分を `write_many` でまとめて書くようにしたあとの状態である。

| 計測（ファイルの記録先） | 変更前 | 変更後 | 変更前（3.14t） | 変更後（3.14t） |
|---|---:|---:|---:|---:|
| 社員 × 月の賞与を登録（72 万セル） | 869 ms | 488 ms | 994 ms | 594 ms |
| 販売数量を按分（22.5 万セル） | 238 ms | 88 ms | 217 ms | 92 ms |
| 1 セルの書き込み（中央値） | 5.0 ms | 5.0 ms | 6.0 ms | 6.0 ms |
| 上の書き込みの後で、スナップショットと記録から開く | 1,808 ms | 50 ms | 1,774 ms | 53 ms |
| 賞与の 1 セルの履歴を引く | 584 ms | 10.5 ms | 527 ms | 9.1 ms |
| 記録の大きさ（スナップショットを除く） | 23.8 MB | 0.8 MB | 同左 | 同左 |

書き込みでは、22.5 万セルや 72 万セルの変更を JSON の文字列にする費用がなくなった（按分では書き込みの時間の 6 割を占めていた）。
開くときは、大量の変更を Parquet から変更の塊として読み、Rust でまとめて書き込む（変更前は JSON の行を Python のリストに直し、1 セルずつ書き込んでいた）。
履歴は、ファイルの記録先では記録を先頭から読むが、変更の塊の中の 1 セルを Rust で探すので、全行を Python にしない。
1 セルの書き込みは、ほとんどがディスクへの書き出し（`F_FULLFSYNC`、1 回約 3 ms）なので変わらない。
